# Multiplayer protocol and deployment

The browser connects to a persistent Node.js process with native WebSocket. `server/index.js` uses the pinned `ws` dependency; no database, account, relay or third-party game service is required. Exactly two reserved slots belong to each six-character room. Room codes are randomly generated; independent 192-bit bearer tokens permit reconnecting to an existing slot. Keep tokens private. Rooms and tokens live only in process memory and are lost on server restart.

Run `npm install`, `npm run build`, then `node server/index.js` from the project. The default listener is `0.0.0.0:8787`; configure `PORT` and `HOST` as environment variables. Open `http://localhost:8787` in two browsers or tabs and create/join a room. The service serves only `dist`, exposes `GET /health`, and accepts WebSocket upgrades only at `/ws`. A static-only host runs offline play; online play needs this Node process.

For public deployment place the process behind an HTTPS reverse proxy with WebSocket Upgrade/Connection headers and an idle timeout exceeding 30 seconds. The client must connect to `wss://your-host/ws` when the page uses HTTPS. Configure `ALLOWED_ORIGINS` as a comma-separated list of exact trusted origins, for example `https://football.example`; an empty list allows all origins for local/LAN testing. Do not expose an unencrypted public ws endpoint as production deployment. Run one process, or add room-aware routing/shared session ownership before scaling to multiple processes. An external proxy should also set connection/IP limits appropriate to the host; this prototype limits per-connection messages and room count, not distributed denial of service.

## Lifecycle and authority

The server creates the entire 22-player match when both connected slots ready. Slot 0 is the host. Settings use `{hostTeam:0|1,duration:60..600,difficulty:'easy'|'standard',tactics:[homeMentality,awayMentality]}`; duration is an integer in active real-time seconds, and each mentality is `defensive`, `balanced` or `attacking`. Host and guest are mapped to team indices independently of the slot number. The host can update all settings in the lobby; a guest may change only their own team's tactic, with all other supplied fields unchanged. Changes reset both ready flags. Neither participant can pause an online match.

Fixed simulation steps run at 60 Hz. Clients submit intentions at 30 Hz; the server snapshots at 20 Hz. The authoritative clock, ball, player positions, possession, selected players, restarts, goals, half changes and final results come only from the shared server simulation. Input acknowledgements name the highest input sequence applied at a simulation tick. Pulsed actions—`pass`, `through`, `lob`, `tackle`, `slide`, `oneTwo` and `switch`—are accumulated between ticks and consumed once. Held `shoot`, `passHold` and `throughHold` buttons let the server accumulate and release charge in the shared simulation. Pass charge caps at 0.75 seconds, with release latches preventing a same-release fallback pulse from launching a duplicate pass. `slide` is a boolean intention to begin a sliding challenge; the server decides eligibility, committed movement, contact order, ball outcome and any foul. Movement is normalised, buttons are type checked, extra input properties are rejected, and non-increasing sequences are rejected. A client cannot report positions or goals.

Connected humans become neutral after 250 ms without new input. A disconnected participant gets AI fallback while the room reserves their slot for 20 seconds. Their private token can reclaim the same slot, match and acknowledgement. A valid rejoin replaces an older socket for that token. Reconnect expiry or explicit departure ends an active match with `state.phase='fulltime'` and `state.result={reason:'disconnect',winner,departedTeam}`. Actual score is preserved. In a lobby, an expired guest frees their slot; an expired host closes the room. Inactive lobbies/results expire after ten minutes. Both players must remain connected and vote to rematch after full-time. Rematch increments `matchId`, resets the match and retains room ownership/tokens/input sequence history.

## JSON messages

Every message is one JSON text WebSocket frame. Client maximum payload is 4096 bytes. A token bucket permits 60 messages/sec with a 90-message burst; input acceptance additionally uses 35/sec with jitter allowance. Repeated malformed requests close the socket; oversize payloads are closed by `ws`. Slow sockets with over 1 MB buffered data are closed. Transport ping/pong checks dead sockets every 15 seconds.

| Direction | Message |
| --- | --- |
| Client → server | `{type:'create',settings:{...}}` |
| Client → server | `{type:'join',code:'ABC234'}` |
| Client → server | `{type:'rejoin',code,token}` |
| Client → server | `{type:'settings',settings:{...}}` — lobby only, guest restricted to own tactic |
| Client → server | `{type:'ready',ready:true}` |
| Client → server | `{type:'input',seq,actions:{mx,mz,sprint,jockey,pass,through,passHold,throughHold,lob,shoot,finesse,chip,strike,clear,tackle,slide,switch,oneTwo,cancelCharge,shotAssist}}` |
| Client → server | `{type:'rematch'}`, `{type:'leave'}` |
| Client → server | `{type:'ping',sentAt}` — RTT probe, numeric client timestamp |
| Server → client | `{type:'hello',protocol:1,tickRate:60,inputRate:30,snapshotRate:20,reconnectGraceMs:20000}` |
| Server → client | `{type:'joined',room,token,ack}` — private to the joining socket |
| Server → client | `{type:'room',room}` — settings/lifecycle updates |
| Server → client | `{type:'snapshot',state,matchId,ack,serverTime}` — private acknowledgement, identical match authority |
| Server → client | `{type:'pong',sentAt,serverTime}` |
| Server → client | `{type:'error',code,message}`, `{type:'closed',reason}`, `{type:'left'}` |

`room` contains `{code,slot,team,host,settings,phase,matchId,players}`. `phase` is `lobby`, `playing` or `finished`; `players` has two entries, either null or `{connected,ready,rematch}`. Internal match `state.phase` retains the finer simulation phases. Tokens never appear in room broadcasts.

Omitted action buttons default to false; the optional `shotAssist` preference defaults to true; supplied buttons must be booleans. In particular, numeric or string `slide`, `passHold` or `throughHold` values are rejected before advancing the accepted sequence. Replaying a previously accepted input sequence cannot queue another action. Deploy matching client and server revisions: older servers reject newer action fields under their strict input schema. Charge meters and receiver guides are local presentation of current authoritative state; the client cannot submit a power value or pass target to override the server's release decision. Goalkeeper contact, catches and parries also run solely in the shared authority.

## Client integration

`new NetworkClient({onRoom,onState,onStatus,onError})` exposes `connect(url)` returning a Promise; `create(settings)`, `join(code)`, `ready(bool)`, `settings(settings)`, `input(actions)`, `rematch()`, `leave()` and `disconnect()`. Call `input` each animation frame; the transport coalesces it to 30 Hz and retains action pulses until sent. `onRoom(roomOrNull)` updates lobby UI. `onState(state,{ack,serverTime,tick,matchId})` receives authority. `onStatus` reports `connecting`, `connected`, `reconnecting` and `disconnected`; `onError(message,code?)` receives actionable errors. Public fields are `room`, `team`, `state`, `latestState`, `latency` (round-trip milliseconds), `status` and `ack`. The read-only `stateAgeMs` getter reports time since the last accepted snapshot, or Infinity before any snapshot.

Use `sampleState()` for rendering. It interpolates positions about 100 ms behind received snapshots and bounds the selected local player's predicted visual movement to at most 0.84 m (120 ms at sprint speed). Each new snapshot reconciles directly to authority before that bounded visual lead. Prediction stops when snapshots are older than 250 ms. Prediction never mutates authoritative snapshots, ball ownership, score or rule state. Teleport/restart discontinuities snap rather than smear. This is lightweight visual prediction, not a full rollback simulation. Network jitter and lower server/frame rates can reduce its smoothness.

Goal replays are local presentation through `client/replay.js`, with no replay, pause or goal-report message sent to the server. An immutable visual history retains about four seconds at up to 20 Hz; an observed score increase can play the preceding three seconds in at most 2.6 seconds during the existing goal phase. Call `record(liveState)` even while playback is active, so a live phase change immediately cancels the replay. The match continues receiving snapshots and submitting neutral human input during playback; the HUD retains authoritative scores. Skipping restores the current live view, and reconnect interruptions or new matches clear/end the relevant playback. Replays cannot mutate authority, spend simulation randomness or delay kick-off for the other player.

Practice is local-only. Its two drill sessions use isolated browser simulation state, create no room and send no training, result or goal-report message. Entering practice closes any previous network session. The title illustration and practice UI are included in the static build, with no external runtime asset request.

The helper retries lost connections with bounded exponential delay during the grace period. It retains monotonically increasing input sequences and resends only unacknowledged input less than 250 ms old; the server drops duplicate sequences. Older actions expire intentionally so reconnecting never unleashes stale kicks. `leave()` abandons the room; `disconnect()` disposes timers and the socket, and a fresh instance should be constructed before another session.

During an active match, a watchdog treats more than three seconds without snapshots as an interrupted connection even if the WebSocket still appears open. It changes status to `reconnecting`, abandons the silent socket, and reclaims the same room using the private token. It does not wait for a potentially stalled close handshake. Quiet lobbies and completed matches do not require snapshots. Online match menus still receive authoritative updates and therefore keep the watchdog active. Opening a socket or awaiting a rejoin response has an eight-second deadline. Connection cancellation settles the pending Promise, and leaving/disposal cancels scheduled retries. Optional constructor fields `snapshotTimeoutMs` and `connectTimeoutMs` shorten those deadlines in tests; production defaults are 3000 and 8000 ms.

Programmatic tests use `createGameServer({port:0,...})`, `await service.listen()`, `service.address()` and `await service.close()`. The exported `rooms` map is an inspection/test seam and is not exposed over HTTP. Tests cover two real WebSocket clients, team/settings sync, slot rejection, input replay/ack, malformed and score-forgery attempts, token reconnect, grace expiry, mutual rematch, health/static containment, oversized messages, flood isolation and the browser helper's automatic reconnect. A real WebSocket relay adds ordered variable 35–120 ms one-way delays to check matching snapshots and acknowledgements. Further cases suppress snapshots while keeping the connection open, verify same-room recovery and stable lobby/full-time behaviour, and exercise silent handshake deadlines, cancellation and late socket events. These are localhost and emulated-jitter tests, not a claim of public-network or physical-mobile latency certification.

Verified on 19 October 2026 with Node.js 24.19.0: `node --test tests/network.test.js` passed all 13 tests in 5.397 seconds. The jitter case compared 24 identical authoritative snapshots and measured a 180 ms probe round trip under the injected 35–120 ms ordered one-way delay. These are measurements from that local run, not throughput or latency guarantees. The test process requires permission to connect to loopback sockets; a restricted-sandbox attempt produced `EACCES` before connecting and was rerun in the permitted context.


`oneTwo` is a one-shot pass-and-run intention, retained until one flush/tick and never a client-specified position or path. `shotAssist` is a validated boolean personal preference; the same authority computes the assisted target for guide and release. The server owns first-time buffer eligibility, expiry/contact, run state, offside and return-pass selection. No client power, queued duration, runner coordinate or goal claim is accepted. Deploy client and server together when using the standalone multiplayer service.
